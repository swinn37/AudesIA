# Page web de démonstration — spécification

Date : 6 octobre 2026. Statut : validée ; plan d'implémentation : [2026-10-06-page-web-plan.md](2026-10-06-page-web-plan.md).

## But

Filmer la démonstration d'Audesia sans ligne de commande : déposer une vidéo, suivre le traitement, relire, corriger ou
régénérer une description, écouter le résultat, puis exporter. En local sur la RTX 5080, un seul utilisateur, un seul
traitement à la fois.

Hors périmètre : plusieurs utilisateurs, authentification, traitements simultanés, déploiement sur le GX10 ou sous
Docker, réglage du « niveau de détail » (le pipeline n'en a pas), avancement détaillé de la voix.

## Composants

| Fichier | Rôle |
| --- | --- |
| `serveur.py` (nouveau) | Serveur FastAPI + uvicorn, déjà installés. Écoute 127.0.0.1 seulement. Lance `audesia_p0.py` en sous-processus, un seul à la fois, et suit son journal. `python serveur.py [--profile small] [--port 8000]` |
| `accueil.html` (nouveau) | Dépôt d'une vidéo, liste des traitements, avancement, liens vers la relecture et l'export. HTML natif, sans ressource externe, utilisable au clavier et au lecteur d'écran |
| `relecture.html` (existant) | Inchangée hors ligne. Servie par le serveur, elle s'active : enregistrer relance la voix et le mixage, Régénérer fonctionne, l'avancement s'affiche |
| `audesia_p0.py` | Nouvelle option `--regenerer ID[,ID]` |

## Traitements

Un traitement est le dossier `out/web/<nom>/`, qui est aussi le dossier de sortie du pipeline :

- `<nom>.<ext>` : la vidéo déposée (la page de relecture prend son titre du nom de la vidéo) ;
- `etat.json` : paramètres (début, fin, voix, profil), commande lancée, `en_cours`, code de retour ;
- `journal.log` : sortie du pipeline, ajoutée à chaque lancement ;
- les fichiers habituels du pipeline (`clip.mp4`, `clip_ad.mp4`, `clip_ad.mkv`, `ad.vtt`, `ad_voice.wav`,
  `relecture.html`, `vision.json`, `descriptions.json`…).

Le nom vient du champ du formulaire, ou du nom du fichier, réduit à `[a-z0-9-]`. S'il est déjà pris, le serveur
ajoute `-2`, `-3`… Au démarrage du serveur, un traitement encore marqué `en_cours` passe à « interrompu ».

Commande lancée :
`python audesia_p0.py out/web/<nom>/<nom>.<ext> --start <début> [--end <fin>] --voice <voix> --profile <profil> --out out/web/<nom>`,
suivie de `--regenerer <id>` pour une régénération. Une relance reprend les paramètres d'`etat.json` : les étapes en
cache sont sautées, et seules les phrases nouvelles sont synthétisées.

## Adresses

| Méthode | Adresse | Rôle |
| --- | --- | --- |
| GET | `/` | `accueil.html` |
| GET | `/api/traitements` | Liste : nom, état, étape, avancement |
| GET | `/api/pret` | Refus éventuel (traitement en cours, Ollama arrêté), demandé par la page avant l'envoi : refusée pendant l'envoi, une grosse vidéo couperait la connexion sans message |
| POST | `/api/traitements?fichier=&nom=&debut=&fin=&voix=` | Dépôt : la vidéo est le corps brut de la requête (`fichier` : son nom d'origine, pour l'extension et le nom par défaut), écrite sur le disque au fil de l'eau, puis vérifiée par ffprobe ; lance le traitement |
| GET | `/api/traitements/<nom>` | État : `en_cours`, `fini`, `echec` ou `interrompu` ; étape (« 5 sur 7 : description, 12 fenêtres sur 79 ») ; 20 dernières lignes du journal |
| POST | `/api/traitements/<nom>/relancer` | Relance avec les mêmes paramètres (après un échec ou une interruption) |
| POST | `/api/traitements/<nom>/corrections` | Corps JSON `{id: texte}` : écrit `corrections.json`, puis relance |
| POST | `/api/traitements/<nom>/regenerer/<id>` | Relance avec `--regenerer <id>` |
| GET | `/api/traitements/<nom>/export/<format>` | `mkv` (`clip_ad.mkv`), `mp4` (`clip_ad.mp4`), `vtt` (`ad.vtt`), `mp3` (piste audiodécrite, bande-son atténuée et voix, tirée d'`ad_mix.wav` par ffmpeg à la demande : c'est la piste que YouTube attend pour l'audiodescription, elle remplace la bande-son), `txt` (script « début – fin  texte », tiré d'`ad.json`) |
| GET | `/t/<nom>/…` | Fichiers du traitement : page de relecture, vidéos (requêtes partielles, pour se déplacer), clips de voix |

L'avancement se lit dans `journal.log` : les lignes `[étape] durée` marquent les étapes finies (extrait, parole, voix
isolée, plans, description, voix, mixage) ; les lignes `k/N … décrit` donnent l'avancement de la description. Les pages
interrogent l'état toutes les 2 s pendant un traitement. Toutes les réponses portent `Cache-Control: no-cache` : les
voix et les vidéos sont refaites sous le même nom à chaque relance.

## Relecture servie

La page déduit le nom du traitement de son adresse (`/t/<nom>/relecture.html`) et interroge
`/api/traitements/<nom>`. Si la réponse arrive, elle passe en mode serveur :

- « Enregistrer » devient « Enregistrer et relancer » : les corrections partent au serveur, au lieu d'un fichier à
  enregistrer et d'une commande à relancer ; le bloc qui explique la commande est masqué ;
- « Régénérer » est actif sur chaque ligne ;
- pendant un traitement, une ligne d'état annonce l'avancement (région `aria-live`), et la page se recharge à la fin.

Ouverte depuis le disque, l'appel échoue et la page reste exactement celle d'aujourd'hui.

## Régénération (`--regenerer`)

Pour chaque fenêtre demandée, avant l'étape « description » :

1. La vision et les détails agrandis de cette seule fenêtre sont refaits, à la température 0,7 : à 0, les mêmes images
   redonneraient mot pour mot la même lecture.
2. La révision et la rédaction sont refaites, à la température 0 comme d'habitude (la nouvelle lecture suffit à les
   faire changer), avec le registre des personnages de `vision.json` et les fenêtres voisines
   de `descriptions.json` (description révisée précédente, description brute suivante, variantes déjà dites).
3. `vision.json` et `descriptions.json` sont mis à jour pour cette fenêtre ; sa correction éventuelle est retirée de
   `corrections.json`.

La suite est inchangée : l'étape « description » lit le cache mis à jour, la voix ne synthétise que les phrases
nouvelles, puis le mixage. Sans `vision.json` (traitement antérieur au cache) ou avec un identifiant inconnu, le
pipeline s'arrête avec un message clair.

## Erreurs

Chacune s'affiche en clair dans la page, dans une région annoncée aux lecteurs d'écran :

- un traitement tourne déjà : refus (409) ;
- Ollama ne répond pas (profil `small`) : vérifié avant chaque lancement, refus (503) avec la consigne de relancer
  l'application Ollama ;
- le fichier déposé n'a pas de piste vidéo, ou pas de piste audio : refus (400), fichier supprimé ;
- une correction vise une fenêtre inconnue, ou n'est pas un texte : refus (400) ;
- le pipeline échoue : état « échec », avec la fin du journal et un bouton « Relancer ».

Sécurité : écoute sur 127.0.0.1 seulement ; noms réduits à `[a-z0-9-]` ; fichiers servis depuis `out/web` uniquement,
sans possibilité d'en sortir.

## Tests

- `python serveur.py --selftest` : lecture de l'avancement dans un journal, réduction des noms, script texte, puis
  les adresses (refus, requêtes partielles, chemins hors de `out/web`, en-tête `Cache-Control`).
- `audesia_p0.py --selftest` : choix des fenêtres à régénérer et retrait de leur correction.
- De bout en bout, dans le navigateur intégré, sur un extrait de 25 s de *Sintel* VF :
  1. dépôt, puis avancement jusqu'à la fin ;
  2. une phrase corrigée, enregistrée, et réentendue après la relance ;
  3. une fenêtre régénérée : texte différent, puis remixage ;
  4. les cinq exports téléchargés et lisibles ;
  5. la page de relecture ouverte depuis le disque, inchangée ;
  6. les refus : traitement en cours, Ollama arrêté, fichier qui n'est pas une vidéo.

## Critères d'acceptation

La démonstration se filme de bout en bout depuis le navigateur : dépôt, avancement, relecture, correction,
régénération, écoute et export, sans ligne de commande, et chaque erreur prévue s'affiche en clair.
